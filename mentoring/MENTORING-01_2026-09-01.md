| 유형 | 의미 |
| --- | --- |
| **핵심 권고** | 프로젝트 성공과 최종 결과 설명을 위해 우선 반영할 가치가 큰 내용 |
| **구현 보완 권고** | 현재 구조를 유지하면서 품질을 높이는 추가 구현 또는 검증 |

| **확장 아이디어** | 현재 1차 프로젝트의 필수 범위가 아니라 여유가 있을 때 또는 차기 단계에서 고려할 내용 |

| **확인 질문** | 멘토가 현재 구현 상태와 설계 의도를 파악하기 위해 확인한 사항 |

# 2. 핵심 권고

## 2.1 최소 서비스 기능을 먼저 실제로 연결

### 멘토 의견

프로젝트의 중심이 인프라 구축과 자동화이므로 Frontend 디자인이나 상용 서비스 수준의 애플리케이션 완성도까지 끌어올릴 필요는 없다. 그러나 프로젝트 주제가 실시간 참여형 오목 서비스인 만큼 **서비스라고 설명할 수 있는 최소 기능은 실제로 동작해야 한다.**

애플리케이션의 기능을 무한히 늘리기보다 프로젝트 제목과 목적을 증명할 수 있는 핵심 흐름을 먼저 완성하고, 이후 장애·복구·부하·확장 검증으로 넘어가는 선택과 집중이 필요하다는 취지다.

### 석판팀 적용 방향

현재 프로젝트에서 먼저 연결해야 하는 흐름은 다음과 같다.

`사용자 진입 → 방 생성·입장 → 팀 선택·Ready → 투표 → 공식 착수 → 게임 결과 처리·저장`

UI가 화려할 필요는 없지만, 단순히 Pod가 `Running`인 상태나 개별 Domain Test만으로 First Success를 완료 처리해서는 안 된다.

### 2026-09-02 확인 상태

**진행 중**이다.

`seokpan-app`에서는 Room, 15×15 Renju, Vote·Turn, Pass, Result·Forfeit·Rating 등 핵심 Domain 규칙과 자동 Test가 구현되어 있다. MariaDB 7개 Table의 SQLAlchemy Model과 Alembic Baseline도 코드화되었다. 그러나 Roadmap상 MariaDB Persistence Adapter, Redis Adapter, Headless HTTP/WebSocket 흐름, Headless First Success E2E, Frontend First Success, Container/Jenkins, Provider/GitOps 통합은 아직 남아 있다.

따라서 **핵심 게임 규칙 구현은 상당 부분 진행됐지만 실제 서비스 First Success는 아직 완료되지 않았다.**

## 2.2 Ansible 자동화의 실행 결과와 재현성을 증명

### 멘토 의견

이미 구축된 인프라만 보여주면 그것이 Ansible 자동화로 구축되었다는 사실을 충분히 증명하기 어렵다. 따라서 다음과 같은 증거가 필요하다고 조언했다.

- Playbook 실행 결과
- 실행 로그 또는 캡처
- 어떤 단계 다음에 어떤 자동화가 실행되는지 보여주는 흐름
- 각 Playbook과 Role이 무엇을 구성하는지 설명하는 자료
- 같은 환경에서 다시 실행했을 때 불필요한 변경이 발생하지 않는지 확인
- 새로운 환경에서도 다시 사용할 수 있는지 확인

실행 당시 증거가 충분하지 않다면 최소한 자동화 구조와 실행 흐름을 다이어그램으로 설명할 수 있어야 한다는 의견도 포함됐다.

### 석판팀 적용 방향

최종 발표와 포트폴리오에서는 단순히 `Ansible 사용`이 아니라 다음을 보여주는 것이 적절하다.

1. 최초 구축 경로
2. 기존 Runtime 재실행 결과
3. 부분 실패 후 재실행 방식
4. 특정 Role·Playbook만 선택 실행하는 방법
5. 실행 전·후 상태와 `changed / failed / unreachable` 결과
6. 완전히 초기화된 환경에서의 재현 여부
7. 수동 구축과 자동화 구축의 시간·개입 횟수 등 비교

### 2026-09-02 확인 상태

**부분 반영**이다.

Kubernetes 자동화는 `cp-01 Bootstrap → cp-02/cp-03 Join → Worker Join → Calico → Gateway API / NGINX Gateway Fabric` 순서로 통합되어 있고, 현재 Runtime 재실행에서는 CP 3대와 Worker 2대 모두 `changed=0`, `failed=0`, `unreachable=0`이 확인됐다. Calico와 Gateway 관련 검증도 통과했다.

반면 완전히 초기화된 신규 Kubernetes 5개 Node에서 `kubeadm init / join / Calico 최초 설치` 전체 경로를 처음부터 수행하는 **Clean Build 실기 검증은 아직 완료되지 않았다.** 관련 Issue에서도 이 점을 MVP 제한으로 명시하고 있다.

프로젝트 전용 Ansible 실행환경의 Version Lock은 상당 부분 진행됐고 빈 Project 실행환경에서 Version Matrix 재생성도 확인됐지만, 관련 Smoke/Rollback Issue의 최종 `failed=0`, Rollback Evidence, 최종 PASS 판정은 아직 남아 있다.

## 2.3 자동화를 모듈화하고 필요한 부분만 재사용 가능하게 구성

### 멘토 의견

자동화는 한 번 전체 구축을 수행하는 스크립트에 그치지 않고 환경이 달라져도 다시 사용할 수 있어야 한다. 전체 `A → Z` 과정 중 특정 기능만 다시 배포하거나 검증할 수 있도록 모듈화된 구조가 바람직하다고 설명했다.

### 석판팀 적용 방향

- Host·Group별 Inventory와 Variable 분리
- 역할별 Ansible Role 분리
- 독립 Playbook 제공
- 통합 Orchestration Playbook 제공
- `--limit`, Tag 또는 독립 Playbook으로 필요한 범위만 실행
- 하드코딩을 줄이고 환경값을 변수화
- 기존 정상 상태에서는 파괴적인 재설치보다 상태 확인 후 필요한 작업만 수행

### 2026-09-02 확인 상태

**부분 반영**이다.

Kubernetes Bootstrap, Control Plane Join, Worker Join, Calico, Gateway Add-on 등이 Role과 독립 실행 단위로 코드화되어 있고 이를 `kubernetes_cluster.yml`에서 통합 실행한다. MariaDB, MaxScale, NFS, Harbor도 역할별 Ansible 코드가 존재한다.

다만 `코드가 모듈화되어 있다`와 `어떤 빈 환경에서도 완전히 재사용 가능하다는 것이 실증됐다`는 다른 주장이다. 후자는 일부 Clean Build 검증이 남아 있으므로 완료로 표현하지 않는다.

## 2.4 관측성을 대시보드에서 끝내지 말고 외부 알림까지 연결

### 멘토 의견

Prometheus, Grafana, Loki, Alertmanager 같은 도구를 선택한 방향은 좋다고 평가했다. 이 도구들은 외부 시스템과 연계할 수 있는 기능을 이미 제공하므로, Dashboard에 경고만 띄우는 것보다 실제 운영자 또는 개발자에게 E-mail, Slack 같은 채널로 알림을 보내는 기능을 구현하면 작은 공수로 운영 기능을 크게 높일 수 있다고 설명했다.

로그에서도 발생해서는 안 되는 오류나 반복되는 오류를 찾아 담당자에게 Routing하는 방식을 함께 고려할 수 있다고 했다.

### 석판팀 적용 방향

MVP에서 이미 정한 Alertmanager E-mail 알림을 우선 실제 동작까지 검증한다. Discord는 선택사항으로 유지한다. 최소 Evidence는 다음과 같이 잡을 수 있다.

- 의도적으로 Alert 조건 발생
- Prometheus Rule 또는 관련 경로에서 Alert 발생 확인
- Alertmanager 수신 확인
- E-mail 실제 수신 확인
- 발생·수신 시각 기록
- 복구 후 Alert 해제 확인

Loki 기반 로그 알림은 일정 여유에 따라 추가한다.

### 2026-09-02 확인 상태

**확인 필요**.

`seokpan-gitops`에는 Alertmanager 설정과 Observability 관련 Manifest가 존재한다. 그러나 현재 확인한 GitHub 근거만으로는 Prometheus·Alertmanager 전체 Runtime이 정상 배포되고 실제 E-mail 또는 Discord 수신까지 성공했다는 점을 확정할 수 없다.

## 2.5 서비스 관점과 클러스터 관점의 대시보드 분리

### 멘토 의견

하나의 Dashboard에 모든 정보를 넣기보다 보는 사람과 목적에 따라 Dashboard를 나누는 것이 좋다고 권고했다.

**서비스 관점**에서는 다음과 같은 항목이 예시로 제시됐다.

- 애플리케이션이 몇 개 실행 중인지
- Traffic이 어떻게 발생하는지
- 서비스 요청 또는 처리 건수

## 2.6 역할별 접근 권한과 계정 관리 체계를 고려

### 멘토 의견

Jenkins, Argo CD, Kubernetes, Grafana처럼 여러 관리 도구를 사용하면 각 도구마다 별도 계정을 운영하게 될 수 있다. 현업에서는 LDAP(Lightweight Directory Access Protocol), OIDC(OpenID Connect), SSO(Single Sign-On) 같은 Identity Provider 연계를 통해 계정 체계를 통합하거나, 최소한 사용자·조직·역할별 권한을 구분한다는 설명이 있었다.

핵심은 `한 사람이 모든 것을 볼 수 있는가`가 아니라 다음과 같은 역할 분리다.

- 개발 조직은 자기 서비스와 Pipeline 범위
- 운영 조직은 인프라와 운영 Dashboard 범위
- QA는 테스트에 필요한 범위
- 조회 권한과 변경 권한 구분
- 다른 조직의 Pipeline이나 Resource를 임의로 수정하지 못하도록 제한

멘토는 4명이 진행하는 교육 프로젝트에서 반드시 별도의 LDAP/SSO 플랫폼을 구축하라고 요구하지 않았다. 작은 규모에서는 하나의 관리자 계정으로도 기능은 동작하지만, **더 큰 조직을 전제로 역할을 나눌 수 있는 구조를 보여주는 것이 프로젝트 설명에 도움이 된다**는 취지다.

### 석판팀 적용 방향

1차 프로젝트에서는 이미 진행한 Kubernetes RBAC(Role-Based Access Control, 역할 기반 접근 제어)를 우선 완성하고 증명한다.

- 담당자별 ServiceAccount
- Namespace별 관리자·조회 권한
- `cluster-admin` 상시 사용 금지
- 허용·거부를 `kubectl auth can-i`로 검증

Grafana·Jenkins·Argo CD의 세부 사용자 역할 분리는 일정에 따라 추가하고, LDAP/OIDC 기반 통합 인증은 후속 확장으로 문서화하는 것이 현실적이다.

### 2026-09-02 확인 상태

**부분 반영**이다.

현재 `seokpan-gitops`에는 `application`, `platform`, `observability`, `cicd` Namespace와 역할별 ServiceAccount/RBAC Bootstrap이 반영되어 있고 Argo CD는 별도 `argocd` Namespace에서 동작한다. Storage 작업을 위해 `storage-infra` Namespace를 추가하는 기준도 확정했다.

## 2.7 Cluster-level DR은 구현 여부보다 현재 한계와 계획을 정확히 기록

### 멘토 의견

현재 4대 Physical PC에 여러 VM을 배치한 구조에서는 Pod 또는 일부 VM 장애에 대응하는 수준과 **Cluster-level DR(Disaster Recovery, 재해 복구)**을 구분해야 한다고 지적했다.

Kubernetes가 Workload 재시작과 Replica 같은 기능을 제공하더라도 그것이 전체 Cluster가 사라졌을 때 다른 환경에서 서비스를 복구하는 DR을 의미하지는 않는다. Physical Server 장애가 여러 구성요소에 동시에 영향을 줄 수 있고, Backup 데이터가 있어도 복구할 실행 환경이 필요하다.

현재 교육 환경과 남은 기간을 고려하면 Secondary Cluster까지 포함한 Cluster-level DR을 완성하는 것은 현실적으로 부담이 크므로, 결과 보고서에서는 다음을 보여주는 방향을 권했다.

- DR을 고려했다는 사실
- 현재 구현한 복구 범위
- 구현하지 못한 범위
- 기간·장비 제약
- 추가 자원이 있다면 어떤 구조로 확장할지
- 프로젝트 성공을 우선하여 후속으로 미룬 판단

### 석판팀 적용 방향

`HA(High Availability, 고가용성)`, `Backup/Restore`, `Cluster-level DR`을 하나의 용어로 묶지 않는다.

- Kubernetes Workload 재시작·Replica → 서비스/구성요소 수준 가용성
- MariaDB Replication·Failover → DB 가용성
- MariaDB Backup/Restore → 데이터 복구
- Ansible 재구축 → 인프라 재생성 수단
- Secondary Cluster + 데이터·Traffic·관리 Plane 전환 → Cluster-level DR

### 2026-09-02 확인 상태

**부분 반영**이다.

MariaDB는 실제 Full Backup → Prepare → NFS Staging → 격리 Restore 검증을 수행했고, 기록된 측정값은 **RTO 3분 23초**다. RPO는 현재 정기 Backup 주기가 고정되지 않아 `최대 Backup 간격` 수준으로만 정의되어 있다. DB Failover와 데이터 무결성 검증도 별도로 수행됐다.

반면 전체 Kubernetes Cluster를 Secondary Cluster로 전환하는 Cluster-level DR은 구현되지 않았다. Kubernetes 자동화 역시 완전히 초기화된 5개 Node에서 Clean Build를 끝까지 검증하지 않았다.

따라서 `DR 구현 완료`가 아니라 **DB 복구와 구성요소 복구는 일부 실증했으며 Cluster-level DR은 설계·확장 영역**이라고 표현해야 한다.

# 4. 현업 관점과 대안 기술 설명

## 4.1 Jenkins와 Tekton

### 멘토 의견

Jenkins는 매우 강력하고 Plugin 생태계가 큰 범용 CI/CD 도구다. Kubernetes에서도 충분히 사용할 수 있으나 Kubernetes에 특화된 기능은 Plugin을 추가해야 하는 경우가 있다.

반면 Tekton은 Kubernetes 환경을 전제로 만들어진 Kubernetes-native CI/CD Framework다. Task를 Container 단위로 다루고 여러 Task를 병렬화하는 방식 등 Kubernetes Object를 직접 활용하기 좋다는 점이 소개됐다.

그러나 레드햇 김명환 멘토님은 **Jenkins를 선택한 것이 잘못된 것이 아니며 현재 Jenkins로 구현해도 전혀 문제가 없다고 명확히 설명했다.**

### 석판팀 적용 방향

1차 프로젝트에서 Jenkins를 Tekton으로 교체하지 않는다.

기술 선택 근거에는 다음과 같이 정리할 수 있다.

- Jenkins: 현재 설계와 팀 작업이 이미 진행됐고 충분한 Pipeline 기능 제공
- Tekton: Kubernetes-native 대안으로 검토 가치가 있음
- 교체 비용과 남은 기간을 고려해 1차는 Jenkins 유지
- 추후 2차 또는 별도 비교 실험에서 Tekton 검토 가능

---

## 4.2 CNCF 생태계 활용

### 멘토 의견

Kubernetes 환경에서는 CNCF에 등록된 다양한 Open Source Project와 Cloud Native 생태계를 이해하는 것이 중요하다고 설명했다. 검증된 구성요소가 이미 존재하는데 동일한 기능을 직접 다시 만드는 것보다 Kubernetes와 자연스럽게 연계되는 도구를 활용하는 것이 효율적이라는 취지다.

### 석판팀 적용 방향

새로운 기능이 필요할 때 먼저 `문제 → Kubernetes 기본 기능 → CNCF/공식 Community Tool → 직접 구현 필요성` 순으로 검토한다.

기술을 추가하는 것 자체가 목표가 되지 않도록 한다.

Gateway API는 Kubernetes Traffic Management를 역할별 Resource로 분리하고 확장하기 위한 표준 API다. 현재 프로젝트는 NGINX Gateway Fabric을 Data Plane 구현으로 사용한다.

### 2026-09-02 확인 상태

## 4.5 Argo CD와 GitOps의 확장 역할

### 멘토 의견

Argo CD는 단순히 하나의 애플리케이션을 배포하는 데만 쓸 수 있는 도구가 아니다. GitOps(Git을 기준 상태로 사용하는 운영 방식)를 이용해 여러 Kubernetes Cluster의 애플리케이션과 정책을 관리할 수 있고, Multi-cluster·DR 구조에서도 활용할 수 있다고 설명했다.

다만 DR 상황에서 Argo CD 자체가 장애 난 Primary Cluster에만 존재하면 관리 기능도 함께 사라질 수 있으므로, 양쪽 Cluster에 관리 기능을 두거나 서비스 Cluster와 분리된 제3의 관리 영역에서 제어하는 방식까지 고려해야 한다고 설명했다.

### 석판팀 적용 방향

현재 단일 Cluster에서 Argo CD를 유지한다. 1차 프로젝트에서는 Argo CD를 실제 GitOps Desired State 관리에 제대로 연결하는 것이 우선이다.

Multi-cluster와 외부 관리 Plane은 후속 확장 설계로 남긴다.

### 2026-09-02 확인 상태

Argo CD Root Application의 공식 Child Application 선언 경로는 `argocd/applications/`로 정리되었고, `storage-nfs`는 `Synced / Healthy`와 NFS Provisioner Running 상태가 기록되어 있다. 현재 `main`의 Child Application에는 `storage-nfs`와 `redis`가 존재한다.

Jenkins·Observability·Frontend·Backend Child Application은 현재 `argocd/applications/`에 아직 존재하지 않는다.

## 5.1 Multi-cluster GitOps

- 둘 이상의 Kubernetes Cluster를 Argo CD/GitOps로 관리
- 같은 정책을 여러 Cluster에 적용
- Primary 장애 시 Secondary Cluster에 Application Desired State 적용
- Cluster별 배포 정책 관리

## 5.2 서비스 Cluster와 분리된 관리 영역

- Argo CD 등 관리 도구를 서비스 장애 영역과 분리

- 대규모 DR 환경에서 Control Plane 성격의 관리 영역 운영

- Jenkins·Grafana·Argo CD·Kubernetes 접근 체계 통합
- 사용자·그룹·조직 역할 관리

## 5.4 운영 Event 기반 자동화

- 장애 시 진단 자료 자동 수집
- 담당자 통보
- 필요한 경우 Ansible Playbook으로 후속 운영 조치

## 5.5 AI 기반 운영 Assistant/Agent

레드햇 김명환 멘토님은 최근 Platform 제품에서 AI Assistant가 YAML 작성, 장애 원인 정리, 보안 Finding 분석, 운영 명령 안내 등에 활용되는 사례를 설명했다. 인터넷이 가능한 실습 환경이라면 AI Agent를 보안·구성 점검에 활용하는 아이디어도 제시했다.

# 7. 팀 운영·문서화·발표에 대한 조언

## 7.1 진행 상황과 문제를 자주 공유

### 멘토 의견

여러 사람이 처음 만나 서로 다른 기술과 성향을 조합해 하나의 프로젝트를 수행하는 것은 어렵다. GitHub 같은 도구를 적극 활용하고 다음 내용을 지속적으로 공유하라고 조언했다.

- 현재 진행 상황
- 막힌 문제
- 앞으로 해야 할 일
- 수정해야 할 내용
- 다른 담당자에게 영향을 주는 변경

`자기 역할만 끝내면 된다`는 방식보다 다른 사람의 작업을 막는 문제를 함께 풀어야 하는 팀 프로젝트라는 점을 강조했다.

### 석판팀 적용 방향

고정된 긴 회의를 새로 만드는 것보다 현재 방식대로 문제 발생 시 즉시 대면 협의하고, GitHub Issue/PR과 주요 Integration Gate에서 상태를 공유한다. 특히 공통 Endpoint, Schema, Namespace, Version, Secret 경계처럼 다른 담당자에게 영향을 주는 변경은 기록한다.

## 7.2 수정 가능한 문서 원본을 남길 것

### 멘토 의견

교육 사업 특성상 HWP나 PDF 제출물이 필요할 수 있지만, 프로젝트가 끝난 뒤 포트폴리오로 다시 구성하려면 PDF만 남기는 것은 수정이 어렵다. Markdown 같은 수정 가능한 형식을 Git에 함께 남기는 방식을 권했다.

AI를 이용한 문서 형식 변환도 충분히 활용할 수 있다고 설명했다.

### 석판팀 적용 방향

- PDF: 공식 제출·열람 기준
- Markdown: 구현 이후 변경, 멘토링, 결정, 트러블슈팅, 포트폴리오 재구성용
- Git: 변경 이력 보존

현재 `seokpan-docs`의 `PROJECT_CHANGES.md`, `MVP_IMPLEMENTATION_BASELINE.md`, `troubleshooting/`, 본 `mentoring/` 영역을 이 원칙에 맞게 사용한다.

## 7.3 자신이 한 일을 정확히 설명하는 연습

### 멘토 의견

많은 일을 해도 설명하지 못하면 외부에서는 수행 여부를 알기 어렵다. 과장할 필요는 없지만 자신이 무엇을 했고 어떤 문제를 해결했는지 명확하게 말할 수 있어야 한다고 조언했다.

작은 진행 공유와 리뷰가 프로젝트 관리뿐 아니라 면접·조직 생활에서 자신의 작업을 설명하는 훈련이 된다는 취지다.

### 석판팀 적용 방향

각 Issue와 PR에 최소한 다음을 남긴다.

- 왜 작업했는가
- 무엇을 변경했는가
- 어떻게 검증했는가
- 실제 결과는 무엇인가
- 아직 안 된 것은 무엇인가
- 다른 담당자에게 어떤 영향이 있는가

## 9.3 완료 여부를 체크박스로 확인하기 좋은 항목

### 서비스·배포

- [ ] First Success E2E가 실제 Runtime에서 통과했다.
- [ ] Jenkins가 실제 Source 변경을 받아 Build·Test를 수행했다.
- [ ] 생성한 Container Image가 Harbor에 실제 Push되었다.

- [ ] WebSocket 연결·재연결을 실제 Gateway 경유로 검증했다.

### 자동화

- [x] Kubernetes 통합 Playbook을 기존 Runtime에 재실행해 `changed=0`, `failed=0`, `unreachable=0`을 확인했다.
- [ ] 완전히 초기화된 Kubernetes 환경에서 Clean Build를 검증했다.
- [ ] Project Ansible 실행환경의 최종 Smoke Test가 PASS다.
- [ ] Project Ansible 실행환경 종료 후 System Ansible Rollback을 검증했다.
- [ ] 자동화 전체 실행 순서를 한눈에 볼 수 있는 자료를 준비했다.

### 관측성·운영

- [ ] Service Dashboard를 실제 Grafana에서 확인했다.
- [ ] Cluster/Infrastructure Dashboard를 실제 Grafana에서 확인했다.

# 10. 1차 → 2차 멘토링 변화 기록

2차 멘토링 직전에는 단순히 체크박스를 채우는 데서 끝내지 않고 아래 표를 갱신한다. 이 표가 포트폴리오에서 가장 직접적으로 재사용할 수 있는 변화 기록이 된다.

| 영역 | 1차 멘토링 직후 문제·상태 | 1차 멘토링 피드백 | 팀 판단 | 2026-09-15 실제 변화 | 검증 결과 | 포트폴리오에서 설명할 수 있는 내용 |
| --- | --- | --- | --- | --- | --- | --- |
| Service | Domain 구현은 진행됐으나 First Success E2E 미완료 | 최소 기능부터 실제 연결 | 인프라 검증이 가능한 최소 흐름 우선 |  |  |  |
| Ansible | 기존 Runtime 멱등성은 검증, Clean Build 미검증 | 자동화 증거·재사용성 강조 | 기존 증적 정리 + 가능한 범위 Clean Build |  |  |  |
| CI/CD | Manifest와 일부 기반 작업 존재, 실제 End-to-End Pipeline 확인 부족 | Image Scan·승인 절차 등 현업 흐름 설명 | 핵심 Jenkins→Harbor→GitOps 우선 |  |  |  |
| Observability | Manifest 존재, 전체 Runtime/외부 알림 근거 부족 | 서비스/클러스터 Dashboard와 외부 알림 | E-mail Alert와 두 관점 Dashboard 우선 |  |  |  |
| Access Control | Kubernetes RBAC 기본 구조 존재, 일부 세부 권한 미완료 | 역할별 접근과 통합 인증 관점 제시 | Kubernetes 최소 권한 먼저 완성, SSO는 후속 |  |  |  |
| DR | DB Backup/Restore 일부 실증, Cluster DR 미구현 | 구현 못 해도 한계와 계획을 설명 | HA·Backup·DR을 구분해 기록 |  |  |  |
| Documentation | PDF와 GitHub 문서 병행 | 수정 가능한 Markdown 원본 권고 | 멘토링·Troubleshooting·결정을 Markdown 누적 |  |  |  |

### 변화 기록 작성 원칙

`기능을 추가했다`보다 다음 구조를 우선한다.

> **멘토 피드백 → 기존 상태 확인 → 팀의 범위 판단 → 실제 변경 → 검증 → 남은 한계**

예를 들어 자동화는 다음과 같이 기록하는 것이 적절하다.

> 기존 Runtime 재실행에서는 멱등성을 확인했지만 Clean Build가 미검증이라는 한계가 있었다. 멘토링에서 자동화 재사용성과 실행 증적의 중요성을 확인한 뒤, 신규 환경 검증 범위를 별도로 분리하고 실행 로그와 실패·재실행 결과를 Evidence로 남겼다.

실제 2차 멘토링 시점에는 측정되지 않은 수치나 수행하지 않은 작업을 채워 넣지 않는다.
